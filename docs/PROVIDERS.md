# Provider verification status (Phase 5)

Written 2026-10-18. This records what was verified, how, and what is still unknown. **Update 2026-10-29:** this file was written before any live call. On 2026-10-28 the OpenRouter text and image adapters ran against the real service and Gnani refused the configured key; see "Live verification (2026-10-28)" at the end. The tables below describe what was known on 2026-10-18. Adapters are still tested with a fake `fetch`, and the default test run blocks the real network (`tests/unit/support/no-network.ts`). "Documented" below means "read in the provider's official documentation", not "tested against the service".

## Modes

- `PROVIDER_MODE` unset or `mock`: the labelled mock brief provider. No network, no usage records.
- `PROVIDER_MODE=live`: OpenRouter for the brief, only if `OPENROUTER_API_KEY` and `OPENROUTER_TEXT_MODEL` are set; otherwise the brief says it is unavailable. It never falls back to the mock silently.
- `PROVIDER_MODE` also decides the image generator: `mock` is the labelled placeholder generator (no network, no cost); `live` is the OpenRouter image model when its settings are complete, otherwise generation is unavailable and never becomes the mock. The generation queue (`/admin/generation`) says which of the three this server is in.
- Transcript translation is decided by `TRANSLATION_MODE` alone: unset or `off` is off, `live` is OpenRouter (only with the key and text model set), anything else is unavailable.
- **A mock-only run therefore sets all three switches** (`PROVIDER_MODE=mock`, `TRANSLATION_MODE=off`, `GNANI_VOICE_ENABLED=mock`); `PROVIDER_MODE=mock` alone leaves translation and live voice as `.env.local` says. The Windows commands are in `docs/DEMO_SCRIPT.md`.
- Voice input is decided by `GNANI_VOICE_ENABLED` alone, independent of `PROVIDER_MODE`: unset means **off**, `mock` means the labelled mock transcriber (no network, no credits), and `true` means live only if `getGnaniSttReadiness` passes. Live speech-to-text is **unreachable** while `LIVE_STT_WIRED` is `false` (see "Voice input (R1-A)" below). Text-to-speech has an adapter but no route or screen.

### Budget rules in force (owner decision)

- 5,000 credits is an absolute ceiling (`GNANI_HARD_CEILING_CREDITS`); `GNANI_BUDGET_CREDITS` can only be lower.
- Because Gnani reports no usage, every call is an **estimate** from the owner's own `GNANI_CREDITS_PER_STT_SECOND` and `GNANI_CREDITS_PER_TTS_CHAR`, rounded up. If either is unset the guard refuses every call (fail closed). A failed call still counts at its estimate.
- Also required: `GNANI_MAX_CREDITS_PER_REQUEST`, `GNANI_CUSTOMER_CREDITS_PER_HOUR`.
- One Gnani call at a time, provider-wide (`maxInFlight: 1`), no automatic retry, never in browser or unit tests.
- Any Gnani call, even a test, needs the owner's explicit approval first.

| Transcript provenance (R1-B) | `src/lib/voice/provenance.ts`. Every transcript the route returns carries a token: an HMAC-SHA256 over the signed-in user, the project, the SHA-256 of exactly that transcript, its source (`mock` or `gnani`, set by the server) and the provider language, valid for 30 minutes. The browser sends it back with "Use this text"; `saveStep` verifies it against its own session user, the project and the text. **Without a valid token (forged, altered, expired, another user, project or text) the description is saved as typed text and no transcript column is written**, so typed text cannot be passed off as a speech service's output through the app. The language comes from the verified token only, never from the browser. Signing key: `VOICE_TRANSCRIPT_SECRET` (server-only, at least 32 characters; required for live mode). Without it, mock mode signs with a random key held by the server process, which can vouch only for mock transcripts and stops verifying after a restart (the text then saves as typed). It is shared through `globalThis`, which works because the dev server and `next start` handle route handlers and server actions in one process; with more than one server instance, set `VOICE_TRANSCRIPT_SECRET` even for the mock, or transcripts from another instance will save as typed. The signed text is the transcript exactly as returned, trimmed again after cutting at the description limit, so it matches what the save receives. Nothing is stored. A token can be presented again until it expires, but only for the same user, project and text, where it changes nothing. **Database rule (R1-C):** customers can no longer write these columns directly; only the server's trusted save path does (see "Transcript column protection (R1-C)" below). |
| Rate limit (R1-B) | `src/lib/voice/rate-limit.ts`, applied after sign-in and before the body is read, in every mode including the mock: per signed-in user, 10 recordings a minute and one at a time; refusals are 429 `RATE_LIMITED` or `BUSY` with `Retry-After`. **Per server process only** (counters in memory, cleared on restart, separate per instance): a guard against a runaway client, not a production quota. The cross-process cost limits for live calls remain the usage ledger's (per-customer credits per hour, one call in flight, the total budget). |
| Storage | **No audio is stored by the application**: it exists only in the request's memory. The route stores no transcript either. Transcript columns are written only by the normal description save (`saveStep` in `src/lib/journeys/service.ts`); the project status is never changed by it (no `TRANSCRIPT_READY`). They are written only by the server's trusted save path, which stores a transcript only with a valid provenance token (below); customers cannot write them directly (R1-C, below). |
| Transcript and language rules | Every description save sets `transcript_original`, `transcript_corrected` and `source_language` explicitly, so none is left stale; only columns whose value changes are written (a typed save on a project that never used voice writes only `requirements_json`, as before). **Transcript chosen** ("Use this text", then save): `transcript_original` = the text as it came back, `transcript_corrected` = the description as saved; a new transcript replaces the old one. **Exact match required**: with the transcript, the browser sends `used`, the text "Use this text" put into the description (after any edits in the transcript box), and sends the transcript only while the description still matches it. The server checks again on its own and keeps the transcript only when the saved description equals `used` after trimming surrounding whitespace. A description edited beyond that match is saved under the typed-text rules: a transcript stored earlier is cleared, and on a project with no transcript only `requirements_json` is written (plus the reset of a stale language described below). **Typed text replaces it** (no transcript sent, description differs from `transcript_corrected`): both transcript columns are cleared. **Saved again unchanged**: the transcript is kept. **Language**: taken from a transcript only when `isLiveTranscriptionWired()` (`src/lib/journeys/voice.ts`: `LIVE_STT_WIRED` and live mode) and the text does not carry the mock label; otherwise it is `"en"`, the value every project starts with. In R1-A that is always `"en"`: a mock run with Tamil selected does not mark the project as Tamil, and any stale non-default language is reset on the next description save. |
| Languages | Codes and labels are separate. Mock mode offers `GNANI_LANGUAGES` (documented codes) or, if none, Tamil (`ta-IN`) and English (India) (`en-IN`), plus **Tanglish as a demo-only selection with no provider language code**. In R1-A the selection only labels the test: the mock ignores it and no selection changes `source_language`. Live mode offers only configured documented codes. **Whether Gnani handles Tamil or Tamil–English code-mixed speech for this account has not been confirmed.** What Tanglish should record once live is still an open decision. |
| Recorder and screen | `src/lib/voice/recorder.ts` (Web Audio capture) and `src/lib/voice/capture.ts` (`VoiceCaptureController`, used by `voice-capture.tsx`). **Audio start**: a context that starts suspended is resumed and must reach `running` within 3 s (`RESUME_TIMEOUT_MS`), otherwise recording is refused with a recoverable message and the microphone and context are released. **Before upload**: a recording with no samples, or shorter than 0.5 s, is refused in the browser and never sent. **One operation at a time** (starting, recording, sending): the screen shows "Starting the microphone…" with Cancel while the browser asks for permission; Stop, auto-stop, Record again and file choice cannot overlap; an auto-stop and a late "Stop and send" send once and never reset the screen during the upload. **Stale results**: each operation has a token; after Cancel, a new operation or unmount, a late microphone grant, auto-stop or upload answer changes nothing. **Cleanup**: Cancel, stop, auto-stop, permission refusal and unmount release the microphone tracks, audio nodes and context; unmount also aborts an upload in flight. **Upload time limit (R1-B)**: an upload still unanswered after the provider timeout (`PROVIDER_TIMEOUT_MS`, default 30 s) plus 15 s is aborted and reported, the screen returns to idle and a late answer is ignored. ## Request limits and the usage ledger

`ai_usage` (migration `20261018000200_ai_usage.sql`, revised after a SQL audit and **applied to the LOCAL Supabase database only**) records every provider call before it is made. `ai_usage_reserve` checks the per-customer limit, the provider-wide ceiling (clamped to 5,000 credits in SQL for Gnani) and the in-flight cap in one serialized transaction; `ai_usage_finish` records the outcome. `audit_events` was rejected as the ledger: it is append-only, admin-read-only and tied to workflow events. OpenRouter limits (all environment-tunable, bounded in code): `AI_BRIEFS_PER_HOUR` (default 5 per customer), `OPENROUTER_DAILY_REQUEST_CAP` (default 40 across the app, below the free tier's 50).

### Interrupted jobs and files left behind

- A job still `QUEUED`/`RUNNING` after ten minutes without progress (`STALE_JOB_AFTER_MS`) is treated as abandoned. This is a recovery heuristic, not proof that the request stopped: only the provider call has a timeout (at most 60 seconds); storage and database calls have none and are never cancelled. `clearStaleJob` refuses a younger job, records the administrator in the audit trail **first** (if that fails, nothing is changed), then removes only that job's own unreleased files, marks it `FAILED` (`STALE_ABANDONED`), moves the project to `GENERATION_FAILED` and never calls a provider.
- If the original request is in fact still running, it cannot finish: marking its job `SUCCEEDED` is conditional on `RUNNING`. Its failure path then removes only its own files and rows, and moves the project only when its own conditional job update matched, so it cannot knock a newer run's project into `GENERATION_FAILED`. **Residual risk:** until that cleanup runs, or if the process dies before it, the late request can still store files and `design_assets` rows on its `FAILED` job, because the database checks only the job's project and the verified payment on insert, not that the job is `RUNNING`. Such files block a new run and are refused by `releaseProject`, but only the proposed database guard below would stop `admin_release_project` itself from publishing them. A database rule refusing asset inserts for a job that is not `RUNNING`, and timeouts for storage calls, are Phase 6B prerequisites.
- A project left in `GENERATING` with no job is resumed only after a minute, so two requests cannot both run the provider.
- A file left by a failed attempt (cleanup failed) is attached to a job that did not succeed. The service therefore refuses to start another run and refuses to release while it exists, and the admin screen shows "Release is blocked". **This screen cannot remove such a file**; a developer must. The database function `admin_release_project` would still publish it if called by other code, which is what the proposal below closes.

### Proposed migrations (design only: NOT applied, NOT in `supabase/migrations`)

1. **Release only succeeded jobs** — `supabase/proposed/20261020000100_release_only_succeeded_jobs.sql` with its `.down.sql`. A small trigger on `design_assets`: an asset can change from unreleased to released only if its job exists, belongs to the same project and is `SUCCEEDED`. A leftover file then makes the whole release fail and nothing is published. No existing function, policy or grant changes; no data is touched; rollback drops the trigger and function. `tests/db/release-invariant.test.ts` applies it in an in-memory database on top of the real migrations and shows both the gap (the current database publishes the leftover) and the fix. It lives outside `supabase/migrations` because the local live suite compares that folder with the applied history; to apply it, the owner moves both files into `supabase/migrations` and runs `npx supabase migration up --local`. Until then the application checks above are the only guard.
2. **Live metered image provider (Phase 6B only)** — an `ai_usage` image operation (the table CHECK `ai_usage_provider_shape` and the shape test in `ai_usage_reserve`), and a larger generated-file limit on the shared `project-files` bucket once the provider's real output size is known. Not written. Rollback would restore the old CHECK and function after exporting and deleting any `image` ledger rows, and set the previous bucket limits.
3. No `admin_start_generation` function is proposed: the administrator check plus the database guards (verified payment, one active job, state transitions) are sufficient, and an audit event records the administrator.
